# 都01の20:21発リクエストによる409を調査

## 結論

対象便のGTFSと経路stepは20:18発・20:50着で一致している。Groupの復路予定生成が、先頭時刻20:03を候補の出発日時20:06へ合わせるため、バス・電車を含む予定全体を3分後へ移動していた。便IDは20:18便のままなので、20:21発として位置APIへ送ると409になる。

これは予定生成時の時刻不整合で、対象便がRealtimeから消えたケースではない。予定と現在時刻で進める設計でも、その予定が固定の便時刻と一致する必要がある。

## 実データと端末ログ

端末ログのTrip `8HwKkwS6KiISIYhhhvZX` と、Firestoreの該当Tripのlegs・scheduleだけを読み取って照合した。`completedLegIndex=0`、`activeLegIndex=1`、方向はinboundで、今回は往路完了後の復路である。

対象バスはroute `006`、trip `08501-1-09-170-2018`、step `step-bus-18ffb7e753b8454db97d641dd7101129`。乗車停留所は渋谷駅前 `0636-06`、降車停留所は新橋駅前 `0737-04`。

| 項目 | 保存された経路step | 保存された復路予定（日本時間） |
| --- | --- | --- |
| 待ち開始 | 20:03 | 20:06 |
| 徒歩開始（3分） | 20:15 | 20:18 |
| 都01発車 | 20:18 | 20:21 |
| 都01到着 | 20:50 | 20:53 |
| 次の電車発車 | 20:58 | 21:01 |
| 次の電車到着 | 21:15 | 21:18 |

候補の `departure_date` は `2026-10-05T20:06:00`。予定行は `generatedBy=route` で、対象バスのride/arrivalとも `legIndex=1`。全行が同じ3分差を持っている。

20:38:45の端末ログでもride予定20:21・arrival予定20:53と、20:21を送るAPIリクエスト、`409 bus_realtime_boarding_schedule_mismatch` を確認した。UTCの11:21は日本時間20:21なので、タイムゾーン変換の問題ではない。

ローカルAPIに同じ不一致パラメータを送って409を再現した。一方、乗車予定をGTFSどおり `2026-10-05T11:18:00.000Z` にすると200。20:38の取得では車両D331、赤坂アークヒルズ前へ向かう状態、車両情報の経過38.3秒だった。

## 元の検索とAPI応答の再現

端末に残っていた実際の復路検索は17:19:33.854の `POST /route`、`start_time=20:04`、`pref=fewTransfers`、日付2026-10-05。出発地は渋谷駅、目的地は十間橋だった。検索開始20:03という逆算は実際のリクエストと一致しない。

同じ条件をローカルAPIに再送すると200、同じ便を含むComfort-1が返った。正規化前のAPIデータは次のとおり。

| データ | 値 |
| --- | --- |
| Candidate.departure_date | 20:06 |
| 最初の徒歩 | 3分、116m、時計なし |
| 待ちminutes | 11分 |
| 待ち時計 | 20:06〜20:18（時計差12分） |
| バス時計 | 20:18〜20:50 |

## 原因となる処理

1. `api/tokyo_route_engine.py:235` 以降は出発地から最寄りノードまでの徒歩を加えた時刻で内部検索を開始する。今回の開始20:04に初期徒歩2分を足すと20:06になる。
2. `api/toei_engine.py:1573` はその内部開始時刻を候補の `departure_date` に保存する。`tokyo_route_engine.py:327` 以降で最初の徒歩を追加・結合した後も、出発地での検索開始20:04へ戻していない。
3. 徒歩分数は切り上げ、待ち分数・時計は切り捨てを使う。最初の徒歩は初期徒歩2分と経路内徒歩の丸めを合わせて3分になる。待ちの整数minutesは11だが時計差は12分になる（`toei_engine.py:467`, `:2161`, `:2307`）。
4. `lib/models/route_models.dart:296` の `_moveLeadingWaitBeforeWalk` は既知の1分精度差を認め、時計差12分を採用する。バス20:18から徒歩3分と待ち12分を逆算し、待ち20:03、徒歩20:15を作る。バスの20:18と候補日時20:06は保持する。
5. `lib/models/group_models.dart:623` は復路に `shiftToStart:true` を指定する。同ファイル `:340` の処理は候補日時20:06と先頭20:03の差を計算し、全時刻へ3分加える。バス20:21・到着20:53・電車21:01となるが便IDは変わらない。
6. `lib/providers/member_mode_provider.dart:889` の `_plannedRideDepartureAt` は経路stepの20:18ではなく、予定行の20:21を送る。APIの `api/app/routes.py:164` の照合でGTFSと一致せず、車両検索前に409になる。
7. `lib/logic/trip_navigator.dart:242` の到着文は元の `StepSeg.arrivalTime=20:50` を使うため、画面と進捗予定20:53も不一致になる。到着による進捗判定には予定行の20:53が渡る。

往路は `shiftToStart:false`、Soloの通常生成もデフォルトfalseで、この一律スライドは起こらない。その他のlegの生成にもtrueの経路がある。また `trip_service.dart:510` の帰り時刻変更は便を選び直さず予定を作り直すため、固定の交通時刻が動く別の入口になる。

## 実行した再現確認

API再実行の先頭3stepを一時的なFlutter診断テストへ渡し、実際の `Candidate.fromJson` と予定生成を実行した。2件とも成功。

- 同じ入力で復路は20:21発・20:53着、往路は20:18発・20:50着となり、保存済み予定と一致する。
- 出発基準だけ元の検索開始20:04へ戻しても、先頭20:03との差で20:19発・20:51着になる。

診断テストは調査後に削除した。アプリ処理・実機状態・保存済みTripは変更していない。

## 修正に必要な範囲

直接の対処は、バス・電車の確定した発着時刻を予定全体のスライド対象にしないこと。集合・待ち・徒歩の調整は、その固定時刻を基準に行う。検索時刻と歩行後の内部検索時刻を同じ `departure_date` として扱う問題、および歩行・待ちの丸めも整理する必要がある。

APIの候補日時だけを修正しても1分差が残るため、それだけでは409は解消しない。今回のTripには既に誤った予定が保存されているので、新規生成の修正に加えて保存済み予定の整合性回復も必要になる。

## 修正後の検証（2026-10-05）

ユーザーが修正した後の `701184b` を検証した。以下の主な対処を確認できた。

- 固定交通を含む復路は、バス・電車の時刻をスライドしない。今回のAPIデータを使う回帰テストで20:18発・20:50着を保持する。
- `shiftToStart` で固定交通を移動しようとすると例外になり、誤った時刻を生成しない。
- 既存の予定行が3分ずれていても、共通のRealtime処理は `Trip.routeStepDepartureAt` / `routeStepArrivalAt` を使う。API送信は便本来の時刻、予定到着の判定も便本来の時刻になる。
- Memberの「今日の予定」は補正済みのナビ用ride/arrival行を表示する。
- バス・電車を含む帰りの時刻変更は経路の再検索を要求する。徒歩だけの再生成では手動予定を保持する。

予定生成、Realtime初期化・送信、Group予定影響、予定調整、Leaderナビ、TripCoordinator、遅延・乗り換え、経路ID、BusLocationSourceの10ファイル、98件のテストが成功した。静的解析はエラーなしだが、既存の `group_models.dart` / `trip_service.dart` に警告・情報11件がある。該当行は修正前から存在することをGit履歴で確認した。

### 残る旧Tripの案内不一致

今回のFirestoreには引き続きバス20:21発・20:53着、電車21:01発・21:18着、ゴール21:25が保存されている。読み取り時にナビ用ride/arrivalだけを補正し、保存データ全体は更新していない。待ち・徒歩・ゴールにも3分差が残る。

旧予定を持つTripについて、補正済みバス到着20:50からの案内を実行する一時診断テストを追加して確認した。

- バスの解決済み到着予定が20:50であることを確認。
- 次の電車の `routeStepDepartureAt` が20:58であることを確認。
- `TripCoordinator.buildMemberNavigationState` の実際のsubTextは **`21:01 半蔵門線 乗車`**。
- 正しい20:58を期待する診断1件が失敗した。

原因は `lib/logic/trip_coordinator.dart:614` 以降のarrival案内が、補正済みの予定ではなく `trip.schedule` の生データを再参照し、次rideの保存時刻を表示すること。新規予定では一致するが、旧Tripでは3分ずれが残る。Group詳細画面も保存された予定を直接表示する。

一時診断ファイルは削除し、実装・正式テスト・保存済みTripは変更していない。
