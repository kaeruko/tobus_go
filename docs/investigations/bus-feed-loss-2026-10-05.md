# 都01の17:02〜17:05の表示停止を再調査

## 結論

17:02〜17:05の「青山学院中等部前・のこり2停留所」は、同じ往路内で404後の古い乗車進捗を保持し続けたことが原因。往路・復路の番号不整合は、この時点の保存データにはない。

17:13の手動往路完了後に発生した `matches=0` は別の派生問題。この例外を17:05の表示停止の原因として説明してはいけない。

対象は都01、route `006`、便 `08501-2-09-170-1616`、車両 `D311`、おでかけ `uBqH8lGSiA8bdeci6w60`。対象のroute stepは `step-bus-4d373de3d0b54d7bb35164eb64863572`。

## 17:05までに確認できた事実

端末に残ったFlutterログと、Firestoreの過去時点の読取を照合した。[抽出した証拠](bus-feed-loss-2026-10-05-evidence.json)に予定行・状態・ログを保存している。

| 17:00:37 | 対象便がAPIから取得できず404。UI進捗は `riding` のまま、`realtimeUnavailable=true`。 |

対象バスのride予定は16:16、arrival予定は17:00。どちらも `generatedBy=route`、`legIndex=0`。往路のcandidateにも同じstepが1件存在する。17:05時点のactive-leg検索でも全Trip検索でも、ride予定は1件に一致する。

添付APIログの `GTFS-RT DROP` は他の路線・車両の記録で、対象D311が解析時に除外された証拠ではない。今回確認したのは対象便のAPIが404になったことと、その後のアプリ状態であり、車両が実際にいつ終点へ到着したかまでは確認していない。

## 元の表示停止が起きる処理

当時の `fe3bdf2` のControllerは、位置情報が200で返った場合にだけ「位置が古く、予定到着を過ぎていたら降車扱い」の処理を実行する。

`bus_trip_not_found` の例外分岐では乗車確認済みのマーカーを残す。`MemberNavProgressNotifier` が最後の `riding` 進捗を保持し、`TripCoordinator` が `arrived=false` を見て予定上の徒歩・ゴールからrideへ戻す。この繰り返しが、17:02〜17:05のログそのものになっている。

17:09の `0c39a6e` は、同じ便の乗車確認済み・404・予定到着後という条件で降車扱いにする修正。今回の元症状に対応するのはこちらであり、17:18の全Trip検索の変更ではない。

## 手動往路完了後の別問題

| 日本時間 | 保存状態・ログ |
| --- | --- |
| 17:13:29.620 | 再起動後の初回pollは乗車進捗なしで往路ゴールを表示。Tripはまだ往路進行中。 |
| 17:13:37.800 | `completedLegIndex=-1`。 |
| 17:13:37.854094 | 手動往路完了に対応する保存更新。比較したフィールドのうち変わったのは `completedLegIndex` だけ。 |
| 17:13:37.900 | `completedLegIndex=0`、`activeLegIndex=1`。対象バスの予定は往路0のまま。 |
| 17:14:29 | 保存履歴から復元された往路の乗車マーカーを追跡し、復路予定だけの旧発車検索で `matches=0`。 |

この問題には、Leg変更をナビセッションの境界にすること、完了したLegの乗車マーカーを復元しないことが必要。全Trip検索は例外を防ぐが、完了済みの往路を追跡し続ける状態までは解消しない。

また、保存履歴は乗車マーカーだけを復元し、古い位置情報を復元しない。現在のLegの乗車マーカーだけが復元された場合も、404・予定到着後なら予定による降車処理へ進める必要がある。

## 今回の修正

- 元症状に対応する17:09の404後の予定到着処理を、往路未完了の条件で再検証する。再起動後に乗車マーカーだけが復元された場合も同じ処理へ進むよう拡張した。
- Groupのactive Legが変わると、共通ナビのController・進捗を作り直す。旧便のポーリングを停止し、切替前に送信したAPI応答は後から返っても反映しない。同じTrip・Legの予定編集では進捗を保持する。
- 保存履歴の読込・保存・表示で、現在のLeg以外の乗車マーカーを除外する。最後に確認した停留所の履歴は保持する。読込中にTripやLegが変わった場合も古い復元結果を適用しない。
- Debugログに `completedLegIndex`、`activeLegIndex`、対象stepの予定行のLeg番号をまとめて記録し、今後は推測に頼らず照合できるようにした。

## 検証の範囲

実機・Firestoreは読取のみ。17:05時点の記録を消したり、おでかけの状態を書き換えたりしていない。

関連する10ファイルのローカルテスト計85件が成功した。往路未完了の200→404、および再起動後に乗車マーカーだけがある404で、予定到着後に進捗が `arrived` となり、UIがゴールへ進んで旧バスに戻らないことを確認した。Leg切替で旧便のpollを止めること、旧API応答・旧履歴の非同期読込結果を反映しないこと、同じTrip・Legの予定編集では進捗を保持することも確認した。

変更したDartコードの静的解析と差分チェックも成功した。修正版を端末へ反映しての実機確認は未実施。

過去時点の取得にはFirestoreの [`readTime`](https://firebase.google.com/docs/firestore/reference/rest/v1/projects.databases.documents/get) を使用した。原本は無視対象の `.dart_tool/leg_navigation_recheck_2026_10_05/` に保存し、この資料には関係するフィールドとログだけを抽出した。
