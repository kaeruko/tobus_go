# 日本語・英語・中国語対応の負荷レビュー

更新日: 2026-09-30

この資料はソースコードの静的レビューです。本番へのアクセス、負荷試験、実測による応答時間・処理能力・料金の評価は行っていません。以下の回数はコードの更新間隔からの概算で、利用状況や依存状態の更新によって変わります。

アプリ内では言語を固定せず、端末の言語設定に従って日本語・英語・簡体字中国語を表示します。端末側の言語を変更すると、対応する表示言語も切り替わります。中国語は簡体字です。

## 今回の多言語化による影響

- UI の翻訳はアプリに同梱し、翻訳 API は利用しません。
- 中国語画面の都営停留所・駅・行先は、既存の英語・日本語フィールドを使って「英語 (日本語)」と表示します。都営 API の中国語取得や言語別経路検索は不要です。[表示処理](../lib/l10n/transit_name_localizations.dart)、[経路リクエスト](../lib/services/route_search_service.dart)
- Places の検索候補は日本語画面では日本語、英語・中国語画面では英語で1回取得し、地点選択後は従来どおり日本語・英語の Details を2回取得します。中国語の Details を追加しないため、地点選択あたりの通信回数は増えません。[地点検索](../lib/widgets/place_field.dart)
- 翻訳文字列の同梱によるアプリサイズ増はあります。サイズ・描画時間は未計測です。
- 端末側の言語変更による表示切替では、経路検索や Realtime の Provider を作り直す必要はありません。取得済みデータは端末内で表示を変更します。
- 「みつける」の編集メモ・画像キャプションは既存の日英データを使用し、中国語画面では英語を表示します。利用者が入力した名前・グループ予定などの自由文も自動翻訳しません。

## 今回解消した無駄な候補検索

`PlaceField._onInputChanged` で IME の未確定文字を送信対象から除外しました。中国語の拼音入力や日本語変換の途中で300ms停止しても、候補検索を送りません。確定後に通常の debounce が働きます。

また、バックエンドの起動待ち後に入力世代と画面の有効性を再確認し、待機中に古くなった検索を送信しないようにしました。[該当処理](../lib/widgets/place_field.dart)

## 残る懸念と改善候補

### 1. 優先度高: 次便 Realtime の強制取得

これは多言語化前からの挙動です。`nextRideRealtimeDepartureProvider` は20秒の ticker と状態変化を監視し、バス・地下鉄とも `forceRefresh: true` を渡します。次便の確認対象が続く場合、ticker だけでも利用者1人あたり約3回/分の取得に加え、依存状態変更による取得が発生し得ます。

通常の45秒キャッシュを迂回し、都営バスではロック取得後も有効期間0として判定します。同時の強制取得がロックで順番待ちになっても、上流取得を1回にまとめる仕組みにはなっていません。地下鉄も強制更新時はキャッシュを使いません。利用者増で上流取得数と待ち時間が増える要因です。

改善候補は、定期更新を通常キャッシュ経由にし、強制更新を利用者の明示操作に限定すること、同時の更新処理を共有することです。鮮度要件と合わせて別途確認してください。

根拠: [20秒 ticker](../lib/providers/minute_ticker_provider.dart)、[次便取得](../lib/providers/delay_impact_provider.dart) の `nextRideRealtimeDepartureProvider`、[バス45秒キャッシュ](../api/app/services/tokyo_realtime_provider.py) の `vehicle_positions`、[更新ロック](../api/app/runtime.py) の `refresh_realtime_bus_positions`、[地下鉄更新](../api/app/services/train_realtime.py) の `get_realtime_vehicles`。

### 2. 優先度中: Places の呼出し数と接続の再利用

これも既存の構成です。候補検索には300ms debounce があり、地点の選択ごとに日本語・英語の Details を2回取得します。中国語 Details を3回目として追加すると、この部分の呼出し数は50%増えるため、今回の仕様では追加しません。

サーバー側では各リクエストで `httpx.AsyncClient` を生成しています。同一要求の進行中処理の共有や検索セッション識別子の受け渡しはありません。すでに送信済みの古い候補検索は、結果を画面に反映しないだけで上流通信自体は継続します。

改善候補は、同一言語・検索語または place ID に対する進行中要求の共有、アプリのライフサイクルに合わせた HTTP 接続の再利用です。保存キャッシュやセッション方式を導入する場合は、別途サービスの現行条件を確認する必要があります。具体的な料金・削減額は本レビューの対象外です。

根拠: [地点選択時の2言語取得](../lib/widgets/place_field.dart) の `_pick`、[Places への接続](../api/app/services/google_places.py) の `autocomplete_legacy_response` / `details_legacy_response`。

### 3. 優先度中: 経路検索の直列化と応答データ量

`/route` はインスタンス内のロックで経路検索を直列化しています。言語辞書の追加では探索量は変わりませんが、利用者増や言語切替に伴う不要な再検索があると待ち行列が長くなります。まずロック待機時間と探索実行時間を別々に計測し、同時アクセス時の応答時間を確認するのが適切です。

クライアントの経路検索は `/route` と、鉄道候補がある場合の `/train/resolve-route-identities` の1〜2段階です。後続リクエストには候補データを含むため、大きな候補では通信量も増えます。これは既存の構成で、今回の中国語対応は都営データに新しい言語フィールドを追加しません。

根拠: [検索エンドポイント](../api/app/route_endpoint.py) の `route_start`、[検索サービス](../lib/services/route_search_service.dart) の `ApiRouteSearchService.search`。

### 4. 優先度中: Realtime の重複・長時間リクエスト

通常の乗車中ポーリングは30秒間隔です。`MemberModeController._checkProgress` には同一処理の実行中ガードがなく、`ApiClient.get` にもクライアント側の明示的な timeout がありません。ネットワークが長く応答しない場合、前回が終わる前に次回が開始し得ます。これは既存の問題です。

改善候補は、処理中の通常ポーリングをまとめること、GET の適切な timeout と中断方法を設けることです。更新中の明示リフレッシュや画面終了時の扱いも合わせて検証してください。`ActiveRouteContent` 側には実行中ガードがあります。

根拠: [メンバーの定期更新](../lib/providers/member_mode_provider.dart) の `_startPolling` / `_checkProgress`、[HTTP GET](../lib/core/api_client.dart) の `get`、[経路画面の実行中ガード](../lib/widgets/active_route_content.dart) の `_refreshRealtime`。

### 5. 優先度中: グループ管理画面の再購読

`LeaderModePage` は画面の再描画ごとに `TripService().streamTrip(...)` を生成しています。既存の1分タイマーに加え、言語切替でも再描画されるため、Firestore の購読が作り直される可能性があります。都営の経路検索とは別の通信です。購読する Stream を画面の初期化時に保持し、trip ID が変わるときだけ更新することが改善候補です。実際の読取回数や課金増は未計測です。

根拠: [グループ管理画面](../lib/pages/leader_mode_page.dart) の `build` と `_clockTimer`。

## 推奨する確認項目

1. 日本語・英語・中国語それぞれで地点を選択し、Details が `ja` と `en` の2回だけであることを確認する。
2. 取得済み経路を表示したまま端末の言語を切り替え、`/route`・Realtime の呼出しが増えないことを確認する。
3. IME 未確定中の入力、起動待ち中の再入力、画面破棄で不要な候補検索を送らないことを確認する。
4. Realtime に同時アクセスを発生させ、アプリ側要求数・上流取得数・キャッシュ利用数を分けて計測する。
5. 経路検索の同時実行数を段階的に増やし、ロック待ち・探索時間・p95 応答時間・timeout・メモリを確認する。
6. 遅い接続や応答停止で30秒ポーリングが重複しないこと、言語変更後も不要な定期処理が残らないことを確認する。

本番での利用者数、上流制限、料金条件、実行環境の同時処理数は未確認のため、現時点で最大対応人数や費用の断定はできません。
