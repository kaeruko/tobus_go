## 「待てる」の意味

駅・停留所の非乗車状態では、その場所で待ち、準備完了時刻以降に出発する任意の利用可能な便を選べる。「最初に乗れる便」だけに選択肢を制限しない。

- 待機は時刻だけを進める。乗車回数、総徒歩、連続徒歩を変えない。現行のコストは辺の重みの合計で、待機時間には加算しない。このコスト定義を維持する。
- 鉄道の乗車準備時間は現行の2分を維持する。準備完了時刻と出発時刻が等しければ乗車可能とし、後続区間で準備時間を再加算しない。
- 鉄道の乗換では現行の降車1分も維持する。列車の停車時刻から別便の準備完了まで、降車1分と新規乗車準備2分を要する。バスの詳細行程はGTFS到着時刻に隠れた降車1分を足さない現行仕様であり、別モードの時間を一律に当てはめない。
- 探索の期限は元の出発時刻から240分。状態ごとに残り240分を与え直さない。待機や乗換もこの共通期限に含める。
- 日付・運行日・利用モード・データ版・リアルタイム情報は同じ検索内で固定する。24時以降の便も運行日からの時刻として扱い、時刻を0時へ巻き戻さない。
- 止まらない停留所、運休便、途中終点など、その便が提供しない行動は選べない。早着だけで利用可能な方向・運行パターンが同じとはみなさない。

待機は新しい非徒歩辺を通るだけで連続徒歩がリセットされる実装にしてはいけない。既存の `board`・`alight`・`xfer` でのリセットや即乗降の扱いは別の仕様問題として残る。今回の3反例はその規則を変更せず成立する。待機の導入に便乗して既存のリセット規則を変更しない。

検索開始時に時刻表managerをコピーし、鉄道数値遅延、バス遅延・車両情報、運休・運行テキスト等の可変データを固定する。静的な時刻表・グラフは検索中にデータ版を差し替えない前提。詳細化もこの検索内の時刻と選択便を使用する。

## 乗車後は同じ便を継続する

後続便を選べることと、乗車中に便を選び直すことを区別する。乗車した後は、具体便の次の停車位置へ進む。途中で別便や反対方向の便に入れ替わらない。

乗車時に利用可能な便へ分岐し、label に具体便と停車順序を持たせる。`SelectedPath` が各辺の時刻・便選択を詳細化へ渡す。静的な路線ノードだけを状態とする方式には戻さない。

| 状態 | 将来の行動を決める情報 |
| --- | --- |
| 非乗車 | 物理ノード、乗車準備の段階、そこで利用可能な路線・方向・運行パターン |
| 乗車中 | 上記に加え、運行日、具体便、現在の停車順序 |
| 検索全体 | 利用モード、データ版、運行日判定、リアルタイム情報、元の出発時刻と期限 |

具体便はデータ供給元・運行日・`trip_id` 等で一意に区別する。ODPTの `train_num` 単独や表示名だけを一意なキーと仮定しない。同じ停留所へ戻る便もあるため、停留所IDだけでなく停車順序を保持する。

- 別便へ移るには降車と新たな乗車を記録し、乗車回数を1増やす。新たな乗車では準備時間などの接続条件を再評価する。
- 同じ便の継続では乗車回数を増やさず、その便の停車時刻・停車順序を使用する。
- 行程の詳細化、GTFS便照合、鉄道便IDの確定は、探索で選択した便を維持する。都合のよい別便へ置き換えて候補を成立させない。
- 実装を具体便の乗車地点→降車地点というleg遷移へまとめても、選択便・通過順序・準備時間・乗車回数を保持する同じ契約が必要である。

従来の鉄道は隣接する `ride` ごとに `get_next_train_arrival()` を呼び、乗車便を保持していなかった。修正後の乗車中の遷移は具体便の次の停車位置に限定し、後段の `train_route_identity.py` も選択したODPT便・時刻・停車順序を検証してからGTFS便IDを確定する。各辺で別の最早到着便を選び直さない。

例えばN1がA 10:00→B 10:05→C 10:20、N2がB 10:07→C 10:08の場合、AからN1へ乗ったままC 10:08着にはできない。現行の降車1分と準備2分ではBでの準備完了は10:08となるため、N2の10:07発への乗換も認めない。別fixtureでN2をB 10:09発→C 10:10着にすれば、接続可能な2回乗車として確認できる。Cの時刻は列車の停車時刻であり、降車後の非乗車状態になる時刻とは区別する。

## dominance を認める条件

残す状態Aが捨てる状態Bを支配するとは、Bの各合法な後続行程をAからも実行でき、目的値と制約資源が悪化しないことをいう。将来の行動集合は、必ずしも完全に等しい必要はない。AがBの選択肢をすべて再現できる包含で十分である。

`cost` と `fewTransfers` は同じ未来状態キー・同じ乗車回数でのみ比較する保守的な規則を採る。各キーで単一の最安値を保存せず、複数の非支配labelを保持する。

```text
label = (future_state_key, boardings, cost, curr_time,
         total_walk_m, exact_seg_walk_m, predecessor)

非乗車状態で A が B を支配するための条件:
  A.future_state_key == B.future_state_key
  A.boardings == B.boardings
  A.cost <= B.cost
  A.curr_time <= B.curr_time
  A.total_walk_m <= B.total_walk_m
  A.exact_seg_walk_m <= B.exact_seg_walk_m
  A から B.curr_time まで待って、B の後続行程を再現できる
```

上の待機契約により、同じ非乗車状態の早着AはBの時刻まで待って同じ便を選べる。現在の「最初の便だけを選ぶ」関数を維持したまま、この時間比較を安全だと扱ってはいけない。

`time` は乗車回数を比較キーから外す。このモードの目的は到着時刻で、乗車回数とcostにハード上限はない。待機可能な同じ非乗車状態で厳密に早着するAは、総徒歩・正確な連続徒歩が同等以下なら、prefix costが高くてもBを支配できる。AはBの時刻まで無料で待ち、同じ後続便を選べるためである。同時刻の場合は従来どおりcostも同等以下とする。これは同一便の継続と不要な乗降を同時刻で比べる際の安いprefixを維持する条件であり、最速到着に加えて全行程costや乗車回数も最小になる保証ではない。

乗車中と待機を証明できない状態では比較キーに時刻が入るため、上の厳密な早着によるcost条件の省略は適用されない。別便・別停車順序を比較せず、合法な環状便を一律禁止しない。同じ後続便に間に合うだけの不要な乗降は統合する。合成の環状fixtureでは508回必要だった探索が80回となり、150回の予算で完走する正式な回帰テストを追加した。

乗車中は別便・別停車順序のlabelを比較しない。同一便・同一停車順序でも時刻が異なる場合、同じ後続便行程を再現できると証明するまでは、時刻一致を比較の条件とする。具体便の時刻が固定された通常の同一状態では同じ時刻になる。バスは同じ便・停車順序・時刻でも、新規乗車直後の即降車が1分、継続乗車後の降車が0分となるため、その段階も未来状態キーに含める。これを省くと安い新規乗車側が合法な終便乗換を消す反例を、3モードの正式テストで確認した。

完全に同じlabelは単一最良経路の探索では統合できる。浮動小数の丸め幅で、より大きな歩行量やより遅い接続時刻を同じとみなさない。途中状態で25m bucketを正確な歩行量の代わりに使わない。到達済みの目的地には後続制約がないため、従来の最終徒歩25mグループごとの候補整理だけを維持する。

生成時とpop時は同じ規則・同じlabel集合を使う。生成前の `g_score` だけ、またはpop後の `best_cost` だけを直すことはしない。pop時には、labelが有効なままかを確認し、別の安いlabelがあるだけで除外しない。

目的値はモードごとに維持する。`fewTransfers` は `(boardings, cost)` の辞書式、`cost` はcost、`time` は到着時刻。将来状態と歩行資源の安全条件を共有しても、目的値の比較まで同一にはしない。`cost` の従来の距離ベース優先度も維持する。逆向きA*下界は `fewTransfers` の優先度だけに使用し、`cost`／`time` の探索順は変えない。

## 複数候補についての範囲

まず3反例で少なくとも1つの完走可能経路を保持し、同じ未来条件を持たない状態をコストだけで消さないことを保証する。

現在の `limit=5` は生候補を5件取得する上限であり、その後の重複除去・便照合を通った異なる合法候補5件を保証しない。今回、この候補取得契約を変更しない。

単一最良経路では支配可能でも、それ以前に使った路線が異なれば別の表示候補として必要な場合がある。異なる乗車履歴の正確な上位k件を保証するには、履歴と重複除去を考慮した別の規則が必要である。今回のPareto化だけで上位k件、候補不足の補充、詳細便照合後の全体最適性まで保証したと説明しない。

### 2026-10-09: 最後の降車・徒歩違いを集約

`cost` と `fewTransfers` の完走状態は、最終徒歩距離の25m区切りではなく乗車行程で比較する。前の乗車区間の降車地点、各区間の路線・パターン、乗車地点、最初の走行先（方向）を保持し、最後の降車地点とその後の徒歩だけを候補の区別から外す。例えば同じ上23出入→草39で、東向島五丁目と向島消防署前のどちらで降りるかだけが違う経路は1つの候補になる。別路線は徒歩距離が同じ区切りに入っても完走状態では消さない。

完走前は従来の便・時刻・正確な徒歩資源による支配判定を維持する。途中の降車状態や同一便の継続を省略せず、そこから別路線へ乗り換える経路を探索できる。代表候補の選択は既存の探索優先順位に従い、完走状態のコストが同じ場合は到着時刻、総徒歩距離の順に比較する。出力済みの行程は再出力せず、後から同じ行程の降車違いが見つかっても候補枠を使わない。選択済み便と時刻は代表経路の `SelectedPath` に保持する。

`time` の最早到着探索、生候補取得数、訪問数・時間・徒歩の上限は変更しない。完走候補枠を異なる行程に使いやすくする変更であり、途中状態の探索や詳細検証後の候補不足の補充、異なる乗車履歴の上位k件を保証するものではない。`cost` の従来ヒューリスティックでは、出力後に同じ行程の安い経路が見つかる可能性があり、すでに出力した代表は差し替えない。

ローカル保存データの平井七丁目付近→東向島六丁目付近、2026-10-09 14:59、`fewTransfers`、生候補5件で確認した。出発座標 `(35.71678, 139.8423)`、目的座標 `(35.72365, 139.8220)` は画像から推定した地点で、画像の正確な座標ではない。修正前の返却4件は最後の降車違い3件と別経路1件、修正後は異なる乗り継ぎ4件だった。ただし訪問数は416→1,241に増えた。同じ416訪問に制限した対照では、修正後は異なる経路2件と既存の探索未完了通知を返し、異なる経路数は増えなかった。目的座標を `(35.7270, 139.8222)` とした近傍例では、修正前後とも358訪問で、最後の降車違い1件がよつぎ小学校前経由の異なる乗り継ぎに置き換わった。候補枠の効率改善と、訪問回数を固定した場合の改善を区別する。

## 実装の受入条件

1. 正式な3回帰テストが、fixtureや歩行上限を緩めずPASSする。
2. 早着状態が、遅着状態から選べる後発の早着便も選べる。後続列車の出発・到着が逆順の合成時刻表を使って確認する。
3. 乗車中の便は維持され、上記N1/N2の例で架空の1回乗車10:08着も、接続時間不足の2回乗車も作らない。N2を10:09発にした別fixtureでは、合法な乗換を2回乗車として残す。
4. 便の途中終点・異なる方向・同一停留所の再訪・運行日・24時超えを状態と便選択で区別する。
5. 待機がコスト・歩行量・乗車回数を変えず、鉄道準備2分と元の出発から240分の期限を守る。
6. 生成時の除外とpop時の除外が同じ支配規則を使う。既存の時刻表呼出回数テストは、必要な情報を確認した後で本当に支配できる入力に限定する。
7. 探索、詳細化、便ID確定が同じ便を使い、合法な候補として最終検証を通る。

上の条件は正式テストで確認済み。その後の実験を経て、下記のfewTransfers A*実装を追加した。下界の意味は「最低残り乗車回数、その最少回数での最低残りコスト」の辞書式の組である。

十間橋→渋谷区役所、2026-10-04 20:40出発では、上限を100000に保ち、正しい探索と便照合で候補を返せるかを次のKPIとする。前処理を含む処理時間、保持label数、pop数、メモリ、最終有効候補数を測る。旧実装の7054回・19423回を達成条件にせず、修正後に再測定する。上限に到達した場合は「経路なし」と混同せず探索未完了として扱う。

## 保存データの移行

ODPTの鉄道時刻表読込で、供給元の便キー・運行日・停車順序を保存し、日付境界を跨ぐ時刻を24時以上へ正規化する。古い `app_data.pkl` はこれらを持たず、SaturdayとHolidayの分離や同番号の別便をpickleだけから復元できない。

ローカル起動では元の鉄道JSONがあれば鉄道時刻表だけ再読込する。Lambdaの配布データには元JSONがないため、コード反映と同時に新しいprebuiltの配布が必要。古いデータのまま起動した場合は不明な便を推測せず、再生成を要求するエラーで停止する。

元のグラフ・バス・リアルタイム設定を保持し、別ファイルへ更新するコマンド：

```powershell
& 'api/.venv-route/Scripts/python.exe' -X utf8 api/refresh_prebuilt_train_runs.py `
  --prebuilt api/data/app_data.pkl `
  --train-timetables api/data/odpt_TrainTimetable.json `
  --output api/data/app_data_search_labels.pkl
```

この更新済みファイルはローカルで作成・測定済み。本番へのアップロード・デプロイは行っていない。

## fewTransfers A*の製品実装

2026-10-05、ユーザーの実装指示により `tokyo_few_transfers_bounds.py` を追加し、共通label探索のfewTransfers優先度へ接続した。逆向きの下界をqueryごとに作成し、目的地キャッシュは持たない。具体便や時刻表、総徒歩を緩和し、連続徒歩だけ25m切捨てで楽観化する。実探索の正確な徒歩・到着時刻・乗車段階・Pareto条件は維持する。到達不能な下界状態も0下界として順序にのみ使用し、下界を根拠にlabelを捨てない。

前処理は既存15秒制限の開始後に行う。グラフ走査・配列生成・逆向き探索の途中から同じ期限確認を呼び出し、時間を超えた場合は `RouteSearchLimitError(reason=time_limit_sec)` で停止する。pop・展開・queue・frontier・旅行時間・歩行の上限は増やさない。

浮動小数点の加算順で下界が過大にならないよう、前向きpop予算と逆向き状態数から全加算の誤差上界を算出し、推定costだけを保守的に下げる。補正量はquery内で固定し、同じ推定値にprefix cost依存の順位差を持ち込まない。goalと0下界は実costをそのまま使用し、candidate costやdominanceにepsilonを入れない。誤差上界が非有限の場合はcost下界だけを無効化し、残り乗車回数の下界は維持する。

既存グラフnodeを目的地とする場合でも、実探索が使う仮想徒歩接続を下界に含める。仮想接続の最大costも数値補正の辺cost上限に含める。通常値域の11.1付近と1e16で加算順の反例を固定し、最安候補を従来と同じ前向きcostで確認した。

正式APIテスト372件PASS。追加の22件は下界の許容性、正確徒歩、便ID・候補順、モード限定、期限、数値補正と仮想接続を確認する。製品コードの再測定は [実装後報告](../benchmarks/few_transfers_pruning_2026_10_04/few_astar_product_report.md) を参照。新モジュールは既存Docker構成に含まれ、依存追加やデータschema変更は不要。本番デプロイは行っていない。

## time A*と絶対到着時刻の丸め

2026-10-05、timeにも最短到着用の逆向き下界を接続した。静的時刻表の「次停留所の到着－現在停留所の出発」の全便・全収録曜日の最小値を使う。待ち時間・具体便・運行日・徒歩資源を下界では緩和し、前向き探索では従来どおり守る。後発早着も含めて最小値を取るため、最初の便だけを残す変更は行わない。未知区間・到達不能状態・独自の時刻評価・便を持たないline開始など、具体便の時刻差を保証できない場合は0下界を使う。

区間最短時間の索引は東京のデータ読込時に作り、managerとGTFS repositoryの寿命に紐づける。queryの浅いmanagerコピーでも完成索引を共有する。データ辞書の差替え・索引version・明示した世代番号を確認し、鉄道読込で既存辞書を変更する前に索引を無効化する。同じ大きさのレコード内編集やバスの入れ子の編集にも `invalidate_static_time_index` が必要。静的データの更新はactive queryと重ねない。目的地・遅延・探索frontierはキャッシュしない。

Realtimeでも同一便の区間両端へ同じ固定遅延を加えるため、実数演算では静的区間差を利用できる。ただし実装のfloat演算は完全には相殺されない。バスでは乗車時刻から逆算した固定遅延が元のroute遅延と1ulp異なる場合もある。`TimeRoundingGuard` は0開始の累積costとみなさず、queryの実時計範囲と元のpop予算から誤差を計算する。

各合法遷移の正確な実時計差は最終到着－現在時刻へtelescopingする。徒歩・準備・降車の加算と、便の2端点への遅延加算の誤差を1遷移につき `ulp(deadline)` で覆う。さらに逆向きの加算誤差と最後の「現在時刻＋下界」の丸めを、query内で固定した保守的な量として控除する。補正するのはキューの見積もりのみ。実到着時刻・candidate・Pareto比較へepsilonは導入せず、goalと0下界は元の時計をそのまま使う。非有限の誤差上界や時計範囲外では下界を無効にする。

目的値は従来と同じ、丸め前の最短到着。表示上同じ分になる場合にも実時計で比較する。同着なら常に全体の最小cost・最少乗換を保証する契約は追加しておらず、同着時の経路は探索順によって変わり得る。cost／fewTransfersの優先度、具体便の継続、総徒歩3,000m・連続徒歩600m、旅行時間240分、pop・展開・キュー・15秒の各上限は維持する。query固有の逆向き前処理も15秒に含め、途中で同じ期限を確認する。

製品コードの測定とテストは [time A*実装後報告](../benchmarks/few_transfers_pruning_2026_10_04/time_astar_product_report.md) を参照。本番デプロイは行っていない。
