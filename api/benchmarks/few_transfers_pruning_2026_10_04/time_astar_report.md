# 東京の time 探索：最短到着用A*と便列挙の再利用

2026-10-05。十間橋→渋谷駅の `time` 検索が候補0件で15秒上限に達した画像を受け、ユーザー指定の **10月5日10:14発** を中心に比較した。

**優先して進めたいのは time 専用A*。** 静的時刻表の試作では、指定入力の現行探索が82,849pop・候補0件で停止する一方、A*は8,797pop・約3.12秒で11:24着の1候補を返した。単に便の列挙結果を再利用する案は処理を速くしても探索量を変えず、同じキュー上限に達した。

今回は実験のみ。製品探索、探索上限、支配判定、具体便の保持、正確な徒歩制約は変更していない。本番HTTP、ライブRealtime、Lambdaの測定も行っていない。静的時刻表での結果なので、画像の15秒超過そのものを再現・解消したとは扱わない。

## A*の下界

`fewTransfers` の乗車回数下界を流用せず、**ここから目的地までの最低所要時間**を逆向きに計算する。静的時刻表の隣接区間について、全便・全収録曜日の `次停留所の到着－現在停留所の出発` の最小値を取る。

待ち時間、運行日の制約、同一便の継続、総徒歩・連続徒歩の制約は下界計算では緩和する。前向き探索では従来の制約をそのまま守る。後発早着も最小値に含め、最初の出発便だけを残すような枝刈りは行わない。

徒歩は製品と同じ速度、鉄道の乗車準備は2分、鉄道の降車・乗換は1分。バスは継続乗車から0分で降車できるため、新規乗車を含め降車時間を下界では0へ緩和する。未知区間・逆向きに到達できない状態は0に戻し、下界だけを根拠に状態を削除しない。

試作は優先度の先頭を `現在時刻＋残り所要時間の下界` に変更した。便・歩行資源・未来状態の比較と安全上限を維持し、下界の前処理も同じ15秒制限内で計時・確認する。

指定入力では18,984node、63,970edge、初期下界37.33分。下界作成は約0.70秒で、61,324バス便・1,161,955停留所時刻・116,658鉄道記録を毎回走査する試作である。製品化時はまず静的区間の最短所要時間索引をデータ読込時に作り、データ更新時に破棄する形が候補になる。索引の事前作成による追加の速度効果はまだ測定していない。

直線距離を固定速度で割るだけの下界は採用していない。現行の保存データ・探索モデルには距離が正でも所要0の区間があり、距離から所要時間を推定すると実際より大きな下界を作り得る。

## 便列挙の再利用

同じ乗車edgeについて、query開始時刻以降の具体便を一度だけ保存し、実際の乗車準備完了時刻で二分探索して利用可能な後続便を返す。後から早い時刻の状態が来ても候補を失わないよう、最初にedgeへ到達した時刻をキャッシュ開始時刻にはしない。

日時・運行便・遅延snapshot・期限はquery内で固定。バスは `予定出発 >= 準備完了時刻－遅延` という元のfloat比較を維持した。`実出発 >= 準備完了` へ代数的に書き換えるだけでは1ulp境界で候補が変わるため、元の索引の予定出発値を保存する。

指定入力の再利用のみでは62,230問い合わせ中52,127回がhitし、138,186便選択肢を保持した。しかしpop・キュー・labelは現行と同じで、探索上限を回避できない。A*との併用でも全入力で追加の時間改善が出たわけではない。先にA*で探索量を削減し、必要なら再利用を別途採用する順序を勧める。

この再利用試作は既存の便列挙の前後で期限を確認するが、列挙内部・最初の鉄道索引作成を途中停止できない。また早い便も保持するのでメモリが増える場合がある。製品化するなら列挙中の期限確認とメモリ評価が必要になる。

## 正しさの確認と残る条件

実験用20テストPASS。A*＋再利用の下で既存の待機・便継続・バス乗車段階の回帰28件も再実行してPASSした。

- 下界実装とは独立した小規模な便・徒歩の列挙で、合法な残り行程に対して下界が過大にならないことを確認。
- 後発早着、途中停留所での追い越し、同一便継続、環状便の停車順序、未知区間・0分区間、virtual destination、鉄道除外を確認。
- 同じ表示分へ切り上げられる経路でも、丸め前に早く到着する候補を優先することを確認。
- キャッシュは時刻の問い合わせ順が逆でも選択肢・便メタデータが一致し、fractional bus delayの1ulp境界でも元のAPIと一致。
- 前処理中の元の期限例外を維持。cost／fewTransfersではtime下界・キャッシュを呼ばない。
- 全16測定の製品source・prebuilt・鉄道GTFS・バスCSV・compiled data・試作sourceのSHA256が現在のファイルと一致。新規4PythonファイルはPython 3.11文法で解析成功。

次の2点を本番化前の条件として残す。

1. **Realtimeとfloat絶対時刻の監査。** この実験のRealtime下界はrideを0へ緩和する安全側の暫定方式であり、ライブRealtimeの性能を測定していない。一定遅延が隣接区間の差で相殺されることは数学的には使えるが、実装のfloat加減算と固定便の時刻比較まで監査してから非0下界へ進む。試作では既存のcost用丸め補正を優先度へ適用しているが、timeの絶対時刻・Realtimeへそのまま本番採用する根拠にはしない。
2. **同着時の契約。** 現行timeは最短到着を目的とし、厳密に早いoffboard状態の支配ではcost差を無視する。全体として「到着が同じなら必ず最小cost・最少乗換」を保証する実装ではない。完走した2入力で候補全体は一致したが、A*で全入力の同着経路まで現行と同じになる保証はない。

0件だった入力で候補を返す効果と、完走した入力で経路を維持して探索量を減らす効果は確認できた。一方、製品timeの最短到着保証に関わる丸め・Realtimeの条件を固める作業は、速度測定とは分けて必要になる。
