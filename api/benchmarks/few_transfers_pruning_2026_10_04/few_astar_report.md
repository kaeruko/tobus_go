## 下界の意味と安全条件

キューの優先度を次へ変更する。

```text
(ここまでのboardings + h_boardings,
 ここまでのcost + h_cost,
 ここまでのboardings, ここまでのcost, 現在時刻)
```

`(h_boardings, h_cost)` は「最低残り乗車回数、その最少回数での最低残りcost」という辞書式の組。costは乗車回数に条件づけた値であり、独立した最小残りcostではない。今回costモードへ転用しない。

逆向きの静的グラフでは、時刻表・運行便・旅行時間・総徒歩上限を無視する。連続徒歩600mだけを25m単位の切捨てで緩め、非徒歩辺では現在の探索と同じく連続徒歩を0へ戻す。実探索の正確な徒歩量やPareto判定は変えない。

```text
floor(開始時の連続徒歩 / 25) + Σ floor(各徒歩辺m / 25)
  <= floor((開始時の連続徒歩 + Σ 各徒歩辺m) / 25)
```

合法な後続行程は、この緩和グラフでも表現できる。そこで辞書式最小値を取るため、合法な後続行程の目的値に対する楽観的下界になる。具体便の途中終点・方向・接続時間を無視した下界経路自体が、実際に乗れる経路だとは扱わない。

元の全63,970辺のcostは非負かつ有限と確認した（最小0、最大約5.902）。バスのみでは鉄道辺を除外して同じ利用モードの緩和を作る。仮想目的地への徒歩も資源とcostに含める。未知ノード・到達不能状態・省略した資源状態は下界 `(0, 0)` へ戻す。下界による枝刈りは加えず、探索順だけに使う。

現在の探索は非支配labelを複数保持し、新しい改善labelを生成時に受け付ける。A*下界を理由に展開済みのnode全体を確定・禁止する処理は追加していない。任意の複数候補の完全一致や厳密な上位k件を理論保証する実験ではない。候補の多様性・履歴による重複除去の契約は従来のままで、今回の6ケース一致は測定結果として扱う。

costはPythonのfloatで加算している。下界の許容性の説明は非負重みの数学的な和に対するもので、前向きと逆向きの加算順による丸めまで同じとは保証していない。今回の全候補一致と独立列挙テストは確認済みだが、極端に近いcostの順位・浮動小数境界を含む本番化の検証は別途必要となる。

## 前処理とメモリ

18,984ノード、63,970辺。徒歩の流入がないノードは正の連続徒歩資源で到達しないため、資源0だけを割り当てる。任意の外部呼出しで省略状態を問われた場合も、安全な0下界へ戻す。

- 単純な全ノード×25状態は474,600、今回の割当は109,968状態。
- 指定目的地では逆向きに97,962状態を処理し、前処理のheap popは129,697回。これは前向き探索2,297popとは別に記録した値。
- 保持配列は1,471,492 bytes（約1.40MiB）、一時CSR配列等は1,590,166 bytes（約1.52MiB）。Pythonのnode辞書・逆探索heap・オブジェクトを含む全量ではない。
- 前処理は全てquery中のメモリ測定に含む。キャッシュの保持コストは今回は含まない。

Windows 11／Python 3.12.10で、更新済みprebuilt・製品compiledバスGTFS loader・静的鉄道GTFS/calendarをロードしたプロセスを測定。探索前RSSは基準約1,203.6MiB、A*約1,203.9MiB。これは鉄道便照合も使用するwarm runtimeに近い範囲で、HTTP実行環境や背景のRealtime処理全体は含まない。[RSS測定の範囲](rss_report.md)と同じ。

OSのPeakWorkingSetSizeを各query終了後に読むため、値はその時点までのプロセス生涯ピークであり、起動ピークも含む。query中の10ms目標サンプリングも保存したが、指定経路では最大間隔が基準約279ms、A*約178msで、短いピークを拾い漏らす可能性がある。サンプル増分は基準約54〜61MiB、A*約2〜4MiBで、正確なオブジェクト割当量とは扱わない。

LambdaはLinux／Python 3.11なので、Windowsのピークを実機MemorySizeと比較して余裕を断定しない。本番のメモリ・時間は今回未測定。
