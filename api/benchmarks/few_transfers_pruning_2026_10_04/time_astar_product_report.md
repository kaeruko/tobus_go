# time A*の製品実装と再測定

2026-10-05、ユーザーの実装指示を受け、東京の最短到着探索へtime専用A*を接続した。**十間橋→渋谷駅、10月5日10:14発は8,797pop・中央値2.530秒、11:24着の1候補を返した。** 実験で毎回行っていた時刻表全体の走査は、データ読込時の索引作成へ移した。リアルタイム遅延の丸めも、絶対到着時計に対する下界として監査・補正した。

製品コードの実装とローカル確認まで完了。本番へのデプロイ、ライブRealtime、本番HTTP、Lambda実機の測定は行っていない。

## 変更

- `tokyo_time_bounds.py`：隣接区間の全便・全収録曜日の最短所要時間索引と、query固有の逆向き下界。
- `tokyo_time_rounding.py`：固定便の時刻代入と遅延加算を含む絶対時計の丸め補正。
- `tokyo_search_labels.py`：timeの優先度へ「現在時計＋残り所要時間の下界」を接続。候補の実時計・資源・支配判定を維持。
- 東京のローカル・Lambda起動処理：データ読込後に完成索引を準備。鉄道時刻表の追記読込前に無効化。

cost／fewTransfersの優先度、総徒歩3,000m・連続徒歩600m、旅行時間240分、15秒・200,000pop・100,000展開・queue・frontier上限は変更していない。逆向きのquery前処理は同じ15秒に含める。便列挙のキャッシュは今回採用していない。

## 絶対時計とRealtimeの安全条件

TimeRoundingGuardは、開始0から所要時間を足し続けるcostモデルを流用しない。実探索には、徒歩・準備・降車時間の加算に加えて、固定便の到着時計へ置き換える遷移がある。

具体便では `departure >= current`、`arrival >= departure`、`arrival <= deadline` を前向き探索が確認する。区間両端に同じfloat遅延が入るため、実数の区間差は静的のままであるが、端点加算の丸めは残る。バスの遅延は「実乗車時計－予定乗車時計」から逆算され、元のroute遅延とは1ulp違う場合もある。この差を無視せず、同じ逆算値が区間両端へ入ることを使う。

各合法遷移の誤差を `ulp(deadline)` で覆い、元のpop予算で全suffixの誤差を上界化する。実時計差の合計は最終到着－現在時計へtelescopingする。逆向きの加算誤差と最後の現在時計＋下界の丸めも固定量として控除し、現在時計より下へは下げない。指定入力の控除は約 `8.63e-7` 分で、候補の実到着時計や支配判定には加えない。

goal／0下界は元の時計を使う。時計範囲外・非有限の誤差計算はヒューリスティックだけを無効にする。未知区間・独自clock evaluator・opaqueな便・便なしでlineから開始するquery・非boardで乗車nodeへ入る接続形状には、安全側の0下界を用いる。到達不能な下界を枝刈りに使わない。

最短到着が目的値である点は従来どおり。同着時の全体最小cost・最少乗換を追加保証したわけではなく、同着経路が探索順で変わる可能性は残る。

## 索引の寿命

完成したrail索引は元manager、bus索引はGTFS repositoryが持つ。queryの浅いmanagerコピーはrail索引を共有する。索引は静的source・区間最小値・版情報だけを保持し、目的地・graph・遅延・deadline callback・label・frontierを保持しない。目的地ごとの逆向き値はquery内で作り、探索終了時に解放する。

source辞書の差替え・索引version・世代番号を検出する。鉄道の追記読込では変更前に無効化する。同じ大きさのレコード内部編集やバスの入れ子編集には、公開した `invalidate_static_time_index` が必要。静的データ更新とactive queryを重ねないという既存snapshot契約は維持する。途中で期限を超えた索引は公開しない。
