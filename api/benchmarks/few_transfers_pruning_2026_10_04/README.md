# 東京「乗換え少なめ」探索の削減案

2026-10-04、十間橋→渋谷区役所・20:40出発の上限エラーを調査。上限100000は変更せず、製品コードや本番設定も変更していない。保存済み東京グラフ・バスGTFSを使ったローカルの静的実験である。

## 原因と探索順の改善

現在は「ここまでの乗車回数、楽さのコスト」の順に処理する。目的地まで残り何回乗る必要があるかを使わないため、少ない回数で途中まで進んだ経路を広く調べる。

この経路の従来探索は100001回処理して0候補。内訳は乗車0回148、1回8370、2回49776、3回41707。4回乗る経路の処理まで進めなかった。

実験で確認した到着候補は4回乗車だが、「4回が必ず最少」という証明ではない。現在の優劣判定に候補漏れがあるため、より少ない乗車回数の合法候補が存在しないかは修正後に改めて確認する。

実験では目的地から逆算して「最低限必要な残り乗車回数と残りコスト」を計算し、探索順を「ここまでの値＋残りの下界」に変えた。実際より厳しい条件を付けない楽観的な下界なので、目的地と無関係な途中枝を後回しにできる。

徒歩は連続600mの制約がある。単純に徒歩を無制限につなげた下界は弱くなるため、連続徒歩を25m単位で切り捨てた緩和状態を使った。時刻表・総徒歩・総所要の条件は下界計算から外し、合法な経路を除外しない方向に条件を緩めた。最終的な探索・候補生成では従来の条件と便照合を使う。

## 実測

| 指標 | 従来 | 探索順を改善した実験 |
| --- | ---: | ---: |
| 処理上限 | 100000 | 100000 |
| 最初の生候補 | 100001回でエラー・0件 | 7054回で取得 |
| 5件の生候補 | 未取得 | 19423回で取得 |
| 重複除去・詳細生成後 | エラー | 2候補 |
| PC上の探索・詳細生成 | 約0.81秒でエラー | 約0.53秒で成功 |

新しい2候補は22:26／22:28到着、いずれも3回乗換。時刻表・行程は前回通常設定で得た候補と同じ内容だった。約0.53秒のうち下界計算は約0.32秒。これらは各条件1回の比較値で、HTTPや鉄道便ID追加照合を含まない。

東京駅→豊洲、新宿→浅草、東京駅→豊洲（バスのみ）の3条件では、従来と実験の候補payloadが完全一致した。新宿→浅草は約0.35→0.30秒に短縮。一方、東京駅→豊洲は約0.12→0.19秒、バスのみは約0.17→0.30秒と、簡単な経路では前処理時間の負担で全体が遅くなる場合があった。常に全目的地用の逆計算を最初から行う実装は推奨しない。共通の逆向き索引・目的地ごとの下界キャッシュ、難しい検索での適用などを含めて検証する必要がある。

## 枝刈りを強める場合

残り乗車回数・コストの下界を使えば、必要な数の有効な候補が揃った後に、それらの上位に入れないと証明できる枝を除ける。最良1件だけを基準に全枝を切ると、利用者へ提示する別候補まで消えるため、候補数・重複除去の仕様も含める必要がある。

現行の比較は場所・徒歩距離bucket・乗車回数に対してコストだけを比較し、到着時刻や総徒歩を考慮しない。これは将来枝刈りを強める場合の懸念にとどまらず、現行実装ですでに合法な候補を失う問題である。`dominance_probe.py` で次の反例を再現した。

- 少し安いバスは乗換地点へ20:58:30着。
- 少し高いバスは同地点へ20:47着。
- 次の列車の最終出発は20:50。
- 両枝がある現在の探索は0候補。遅い安い枝だけ取り除くと、早い枝から1候補が得られる。

このため、単なる「安い」「目的地に近い」「同じ場所へ来た」という理由で削るのは適切でない。到着時刻・歩行資源・乗換回数・同じ後続便を選べる条件を揃え、本当に劣る枝を比較する必要がある。後発便の方が早く着く時刻表をどう選ぶかも整理する。

`opinion_walk_probe.py` でも、現行コスト式と上限を変えずに2種類の候補漏れを再現した。

- 総徒歩2,600mの安い枝と2,300mの少し高い枝が、同じ時刻・乗車回数・連続徒歩0mで合流する。最後に500m歩くと、前者は総徒歩上限3,000mを超える。現行は後者を落として0候補になるが、安い枝を削除すると2,800mの合法な候補が1件出る。
- 連続徒歩599mの安い枝と576mの少し高い枝が同じ25m bucket 23で合流する。最後の10mは576m側しか歩けない。現行は576m側を落として0候補になるが、安い枝を削除すると586mの合法な候補が1件出る。

引用意見の「総徒歩590m／300mのあと400m」は、総徒歩上限3,000mに対する反例にはならない。途中乗車で連続徒歩がリセットされていれば990m／700mとも総徒歩上限内であり、リセットがなければ双方とも連続徒歩上限600mを超える。問題の趣旨は上記の別の数値で再現できる。

早着が遅着を支配するためには、早着状態が同じ後続便を待って選べる必要がある。現行の `get_next_train_arrival()` は出発可能な最初の列車を返す。保存済み東京時刻表の確認では、休日の巣鴨新田→大塚駅前に08:55発09:01着／08:56発09:00着があり、準備時刻08:55では09:01、08:55:30では09:00が返る。後発早着の入力で到着時刻の単調性が成立しない。これは読込データと関数の挙動の証拠であり、実際の列車が物理的に追い越すとの断定ではない。

既存の `test_dominated_or_equal_cost_boarding_skips_timetable_lookup` は、同じ徒歩量で安い枝が10:10、高い枝が10:11のため、高い枝を落とす結果自体は妥当。ただし「時刻表を読まずコストだけで除外できる」という性能上の期待は、安全な条件に限定する必要がある。関連の既存テスト8件は通るが、上記の反例をカバーしていない。

即乗降や物理地点の再訪を一律禁止する場合も、環状路線や有効な乗換まで除外しないか検証が必要。現在は非徒歩の辺で連続徒歩距離をリセットするため、同じ場所で乗ってすぐ降りる経路の扱いは、単なる高速化に加えて歩行上限の意味を整理する変更になる。

## 推奨順序と限界

本番化の推奨順序を訂正する。先の「下界による探索順を先に採用」という順序では、不適切なコスト比較の勝者が探索順によって変わる問題が残る。次の順序が妥当である。

1. 到着時刻・総徒歩・連続徒歩の候補漏れを正式な回帰テストにする。
2. 待って後続便を選べる条件、乗車中の便など将来の継続可能性、歩行上限と複数候補の契約を確認する。
3. 同じ継続可能性を持つ状態について、コスト・時刻・総徒歩・正確な連続徒歩を比較する複数の Pareto label を保持する。生成前の `g_score` と pop 後の `best_cost` の両方を整える。
4. 残り乗車回数・コストの下界を探索順へ導入する。
5. 逆向き索引・目的地キャッシュ・難しい検索への適用を検証し、安全に証明できる枝刈りを追加する。

2は3の前提なので、引用意見の手順3を手順2より先、または同時に扱う。複数 label を持つだけで、早着による支配や異なる経路候補の維持まで自動的に保証されるわけではない。下界の試作・計測は並行して進められる。

今回の下界は「最低残り乗車回数、その最少回数での最低残りコスト」という組を辞書式に比較する。後者を、乗車回数に関係ない独立した最小コストの下界として扱う説明は正確ではない。

実験では現在の不適切な優劣判定をそのまま使った。下界の安全性と、探索全体が全ケースの最適経路・複数候補を保持する保証は別である。3条件の一致だけで後者を証明していない。優劣判定の修正で保持状態数が増えるため、7054回・19423回という処理回数や時間は修正後に再測定する必要がある。本番への採用前には、時刻表の境界、終便、徒歩上限、経路の多様性を含む検証が必要。

2026-10-04の追加確認時点の GitHub main は `a2c322231df105818bc91d12c11f3c2289fab305`。実験対象のローカル `23157251b74999c8a3affa368dc195fa22cff980` から main に追加された変更について、`api/toei_engine.py` と `api/tests/test_tokyo_search_performance.py` の差分はなく、本意見のコード上の指摘は現在の main にも該当する。製品コードと正式テストは変更していない。
