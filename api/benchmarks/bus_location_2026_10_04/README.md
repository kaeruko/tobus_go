# 都01・新橋9:20発のローカル検証（2026-10-04）

指定便 `route_id=006` / `trip_id=08501-2-09-100-0920` は、ローカル静的GTFSでも実際のリアルタイム配信でも照合できた。提供された9:31:56のログでは一致車両0件だったが、9:34以降の再問い合わせでは一致車両が取得できた。少なくとも今回の便IDに固定的な不整合は確認されなかった。

404時に「待機中」と表示する経路はアプリ側に存在する。これは発車待ちを確認した表示ではなく、進捗情報がない場合の表示である。

## AWSログの追加確認

ユーザーの「発車予定9:20から11分間ずっと待機中だった」「途中からローカルAPIへ切り替えた」という情報を受け、同日のCloudWatchを読み取った。設定変更は行っていない。LambdaのURLがユーザーのログにあるURLと一致することを確認したうえで、`us-west-2` の `/aws/lambda/toeigo-api` を09:15〜09:40（日本時間）で検索した。

**対象便の記録は26件あり、全件が `bus_trip_not_found`。うち09:20:16〜09:30:16の11件は、毎分1回、すべて指定便0件だった。** ユーザーの11分間の継続した表示と整合する。単発の404だけではなかった。

検索範囲内では、AWS側の対象便の最終記録は09:30:16で、09:31以降の対象便ログはなかった。提供された09:31:56のローカル404、09:34以降のローカル200という時系列と整合する。

ただし、これらの件数は元配信を解析し、静的GTFSと照合した後の一覧に対する件数である。`api/toei_engine.py:3085`〜`3132` は静的便・停留所番号を解決できない車両を記録なしで除外するため、**当時の元配信に便がなかったのか、解析・静的照合で除外されたのかはAWSログだけでは確定できない。** 車両ごとの元データや除外理由は保存されていなかった。
